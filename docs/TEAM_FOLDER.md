# 多人共用：公司資料存放系統（方案 A）

適用情形：數人共同設計同一案，各人在自己的電腦使用 midas-curve-gen、Midas Civil、RC 構件設計工具（瀏覽器）、StructAudit-AI，
**所有正式檔案放在公司資料存放系統的專案資料夾**（網路磁碟、NAS、SharePoint／OneDrive、Synology Drive 等皆可）。
工具本身不連線、不需架伺服器；檔案是否一致靠四件事：**資料夾結構、檔名、專案狀態表、輸入雜湊**。

範本：`docs/team-folder/範本/{案號}_{案名}/`（由 `docs/team-folder/build.js` 產生；整個資料夾複製到公司系統後改名即可）。
串接規格見 [INTEGRATION.md](INTEGRATION.md)；本文件是 §7.1 第 3 項「多人共用」的使用者決定（2026-11-08）。

## 1. 資料夾結構

```
{案號}_{案名}/
├─ 00_管理/             專案狀態表.xlsx（構件狀態、模型版次、審查紀錄、說明）
├─ 01_線形與建模/        midas-curve-gen 線形檔、Midas 工作模型（只有分析負責人編輯）
├─ 02_分析發行/
│   ├─ R01/             發行的完整 .mct（＋.mcb）與內力表；發行後不再修改
│   └─ R02/ …
├─ 03_構件設計/
│   └─ {構件ID}/         目前版本的案件檔、計算書 PDF、Excel（同一組雜湊）
│       └─ 舊版/         被取代的版本
├─ 04_審查/
│   └─ {構件ID}/         StructAudit-AI 審查報告、調整後案件檔
├─ 05_送審定版/
│   └─ {批次}/           送審的計算書（改名、唯讀）
└─ 99_參考/              規範、來函、會議紀錄
```

## 2. 命名規則

**構件 ID ＝ Midas 結構群組名稱 ＝ RC 構件設計工具的「構件名稱」**（例 `P1_COL`、`P1_CAP`、`P1_PL3`、`S1_DECK`；群組命名見 midas-curve-gen README）。
用英數與底線，不用空白與 `\ / : * ? " < > |`。三者一致，計算書、審查報告、狀態表才對得起來（StructAudit-AI 的配對核對會比對構件名稱與內力來源群組）。

| 檔案 | 檔名 | 產生者 | 位置 |
|---|---|---|---|
| 線形檔（參數內嵌） | `{案號}_線形_{nn}.mct` | midas-curve-gen（另存時改名） | 01 |
| 發行的完整模型 | `{案號}_模型_R{nn}.mct`（.mcb 同名） | 分析負責人 | 02/R{nn} |
| 內力表 | `{案號}_BeamForce_R{nn}.txt`、`{案號}_PlateForce_R{nn}.txt`；分檔時加範圍，如 `_P1-P4` | 分析負責人 | 02/R{nn} |
| 案件檔 | `{構件ID}_案件_{雜湊8}.json` | RC 構件設計工具「儲存案件」**預設檔名** | 03/{構件ID} |
| 計算書 PDF | `{構件ID}_{計算書名稱}_{雜湊8}.pdf` | 工具「列印」另存 PDF 的**預設檔名** | 03/{構件ID} |
| Excel 計算書 | `{構件ID}_RC柱計算書_{雜湊8}.xlsx`（梁版為 `RC梁版計算書`） | 工具「匯出 Excel」預設檔名 | 03/{構件ID} |
| 審查報告 | `{構件ID}_審查報告_{雜湊8}_SR-{日期-時間}.pdf`（.xlsx、.json 同名） | StructAudit-AI 下載預設檔名 | 04/{構件ID} |
| 調整後案件檔 | `{構件ID}_案件_{雜湊8}_審查調整.json` | StructAudit-AI | 04/{構件ID} |
| 送審計算書 | `{案號}_{構件ID}_計算書_D{nn}.pdf` | 送審時人工改名 | 05/{批次} |

- **雜湊8**＝計算書表頭「輸入 SHA-256」的前 8 碼（案件輸入的雜湊，不含存檔時間、構件清單、需確認勾選與審查紀錄）。
  同一版輸入的案件檔、PDF、Excel、審查報告檔名都帶同一組雜湊，在資料夾裡排在一起，一眼看出是不是同一版。**不要手動改雜湊。**
  審查報告與調整後案件檔帶的是「被審查那一版」的雜湊；設計者套用審查建議、重算存檔後會得到新的雜湊。
- **模型版次 R{nn}**：每次重跑 Midas 分析並發出新的內力表就加 1。版次寫在模型與內力表檔名，工具會把這兩個檔名寫進計算書「內力來源」，
  所以**看計算書就知道用哪一版內力**。用「貼上」匯入內力表時，計算書只記得模型檔名，因此模型檔名一定要帶 R。
- **設計版次 D{nn}**：每次送校核或送審加 1，記在狀態表；工作檔名不帶 D（靠雜湊區分），送審定版時才寫進檔名。
- **審查版次 V{nn}**：記在狀態表「審查紀錄」頁。

## 3. 作業流程

| 步驟 | 誰 | 做什麼 |
|---|---|---|
| 1 開案 | 組長 | 複製範本、改資料夾名；狀態表「構件狀態」列出構件 ID、模組、設計依據、設計者、校核者；依第 5 節設資料夾權限 |
| 2 分析發行 | 分析負責人 | Midas 分析 → 匯出完整 `.mct` 與內力表到 `02_分析發行/R{nn}/` → 狀態表「模型版次」加一列（變更內容、可能影響的構件）→ 通知設計者；已發行的 R 資料夾設唯讀，不再修改 |
| 3 設計 | 設計者 | 見下方 3a～3e |
| 4 審查 | 審查者 | 取構件資料夾**同一組雜湊**的 PDF 與案件檔跑 StructAudit-AI；配對須為「已核對」；報告存 `04_審查/{構件ID}/`；「審查紀錄」加一列；有調整後案件檔時狀態改「審查退回」並通知設計者 |
| 5 回修 | 設計者 | 「開啟案件」選調整後案件檔 → 工具通知改了哪些欄位並重算 → 確認判定後存新版（新雜湊）→ 回到 3d |
| 6 模型改版 | 分析負責人、設計者 | 新的 R 發行後，狀態表「內力最新」欄對內力版次不是目前版次的構件自動顯示「需更新」；設計者重新匯入，或確認不受影響並在備註寫明理由後把內力版次改成新版次 |
| 7 送審定版 | 組長 | 確認全部「已核可」、內力皆「最新」、配對皆「已核對」→ 把 PDF 複製到 `05_送審定版/{批次}/` 改名、設唯讀；狀態表填送審批次與設計版次 |

設計（步驟 3）：

- **3a 開始前**：狀態表該構件「編輯中」空白才可動手，填上自己的名字（或在構件資料夾放一個空檔 `_編輯中_{姓名}.txt`）。公司系統有簽出（check-out）功能時用簽出。
- **3b 從共用資料夾「開啟案件」**最新的案件檔。瀏覽器的自動保存只在自己的電腦，別人可能已經更新過，不要直接接著瀏覽器裡的舊狀態做。
- **3c 從 Midas 匯入**時選 `02_分析發行/R{nn}/` 裡的模型與內力表，不要用自己電腦裡的副本。
- **3d 存檔**：「儲存案件」與「列印 → 另存 PDF」（需要時再「匯出 Excel」），三個檔用**預設檔名**，雜湊相同；放進 `03_構件設計/{構件ID}/`，舊的一組移到 `舊版/`。構件資料夾裡只留目前這一組。
- **3e 更新狀態表**：內力版次、設計版次、雜湊、D/C、判定、狀態（待校核）、最後更新，最後清掉「編輯中」（或刪掉 `_編輯中_` 檔）。

計算書出現「匯入後載重表已修改」或「斷面或材料已與匯入時不同，須回 Midas 重分析」時：前者在備註說明修改原因；後者通知分析負責人排入下一個 R，該構件不能送審。

**構件清單**（工具頂列）只在自己電腦整理用：共用資料夾以「一構件一案件檔」為準，不要把多人的構件清單合存成一個檔（容易互相覆蓋）。
「批次計算總表 → 匯出 CSV」的最後兩欄（輸入 SHA-256、內力來源）可直接貼到狀態表。

## 4. 同時編輯與衝突

- **一個構件同時只有一人編輯**（步驟 3a）。工具在各人電腦上執行，不會互相干擾；衝突只發生在共用資料夾的檔案。
- **專案狀態表**：公司系統支援共同編輯（SharePoint、OneDrive、Google 雲端硬碟）時線上編輯；一般網路磁碟上，第二個人開啟 Excel 會是唯讀，
  所以**開啟、更新、存檔後立刻關閉**，不要一直開著。
- 同步軟體產生「衝突副本」（conflicted copy）時：比對檔名雜湊與狀態表，保留與狀態表一致者，另一份移到 `舊版/` 並在備註記錄。
- 案件檔是一般 JSON：公司系統若有版本紀錄，仍照第 3d 步把舊版移到 `舊版/`（檔名不同，系統的版本紀錄不會把它們視為同一檔）。

## 5. 權限建議

| 資料夾 | 寫入 | 其他人 |
|---|---|---|
| 00_管理 | 全員（狀態表） | — |
| 01_線形與建模 | 分析負責人 | 唯讀 |
| 02_分析發行/R{nn} | 分析負責人，發行後改唯讀 | 唯讀 |
| 03_構件設計 | 設計者 | 唯讀（審查者） |
| 04_審查 | 審查者 | 唯讀（設計者） |
| 05_送審定版 | 組長，放入後改唯讀 | 唯讀 |

公司系統不能逐資料夾設權限時，照表約定即可；至少把已發行的 `02_分析發行/R{nn}` 與 `05_送審定版` 設唯讀。

## 6. 送審前的一致性檢核

每個構件逐項確認（狀態表欄位與計算書對照）：

1. 計算書表頭「輸入 SHA-256」前 8 碼 ＝ PDF 檔名的雜湊 ＝ 案件檔名的雜湊 ＝ 狀態表「輸入雜湊」。
2. StructAudit-AI 配對結果為「已核對」（輸入雜湊、模組、構件名稱、內力來源群組都相符）。
3. 計算書「內力來源」的模型檔名版次 ＝ 狀態表「模型版次」頁的目前版次（「內力最新」欄為「最新」）。
4. 計算書沒有「斷面或材料已與匯入時不同」；有「匯入後載重表已修改」者，備註已說明原因。
5. 審查紀錄的結論為「核可」或「修正後核可」，且審查的雜湊就是目前這一版（修正後重算者，須以新版再審或由審查者確認）。

## 7. 工具配合（2026-11-08）

- RC 構件設計工具：「儲存案件」預設檔名 `{構件}_案件_{雜湊8}.json`、列印另存 PDF 預設檔名 `{構件}_{計算書名稱}_{雜湊8}`、
  Excel `{構件}_RC柱計算書_{雜湊8}.xlsx`（原為日期時間）；構件總表 CSV 增加「輸入SHA-256」（前 16 碼）與「內力來源」
  （模型／內力表／群組，並標示「匯入後已修改」「斷面或材料已變更，須重分析」）兩欄。
- StructAudit-AI：審查報告下載檔名 `{構件}_審查報告_{雜湊8}_{報告編號}`、調整後案件檔 `{構件}_案件_{雜湊8}_審查調整.json`
  （計算書沒有構件名稱與輸入雜湊時，沿用報告編號與原案件檔名）。
- 工具不讀寫狀態表、也不鎖檔：一致性靠本文件的流程與第 6 節的檢核。團隊變大、需要自動鎖定或線上共同編輯時，再評估方案 B（共用網頁＋伺服器存檔）或 C（版本控制）。
